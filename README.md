Predicting a diabetes diagnosis from 100,000 patient health and lifestyle records —
and a documented investigation into why an earlier version of this project claimed
100% accuracy, and what that number actually turned out to mean. This is a rebuild
of an [earlier Portuguese, notebook-only version](assets/) of the same project (see
the two original screenshots in [`assets/`](assets/)): rewritten in English as a
tested Python package with a training pipeline, a Streamlit dashboard, and Docker
support.

## Problem statement

Given demographics, lifestyle, vitals, and lab results for a patient, predict whether
they've been diagnosed with diabetes (`diagnosed_diabetes`, binary). The dataset has
100,000 patients and 30 predictive columns; see [`data/README.md`](data/README.md)
for the full column list.

## Methodology & the data leakage finding

An earlier version of this project trained a `RandomForestClassifier` and reported
100% accuracy. Rebuilding it surfaced two separate problems behind that number.

**1. An inverted train/test split.** The original notebook computed
`test_size = 1 - train_size` with `train_size = 0.005`, then passed that `test_size`
into `train_test_split`. The model trained on 0.5% of the data and was "tested" on
the other 99.5% — backwards from normal practice.

**2. Two columns that leak the target.** Fixing the split direction alone barely
moved accuracy, which pointed at the feature set itself. Two columns turned out to
leak `diagnosed_diabetes` directly:

- `diabetes_stage` maps to `diagnosed_diabetes` with **zero exceptions** for 3 of its
  5 values (`No Diabetes` and `Pre-Diabetes` → always 0, `Type 2` → always 1) — it's
  effectively the target under a different name.
- `diabetes_risk_score` correlates strongly with the target (mean 32.3 for diagnosed
  patients vs. 27.1 for non-diagnosed) and is almost certainly a composite score
  computed downstream of the diagnosis rather than an independent predictor.

To make the effect visible rather than just fixing it silently, every model here is
trained on three named feature sets ([`features.py`](src/diabetes_prediction/features.py)):

| Feature set | Description |
|---|---|
| `full` | Everything, including the two leakage columns — reproduces the original's inflated result |
| `realistic` | Leakage columns removed — the **deployed** model. Keeps `hba1c`/glucose columns, since those are legitimate clinical inputs a doctor would have *before* diagnosing |
| `minimal` | Also drops lab results — demographics + lifestyle + vitals only, approximating a non-invasive screening scenario |

## Results

5-fold cross-validated, 80/20 train/test split, `random_state=42`. Full numbers,
confusion matrices, and ROC curves for every run are in
[`reports/metrics.json`](reports/metrics.json) and `reports/figures/` (generated by
`train.py`; not committed, see [Running locally](#running-locally)) and browsable in
the dashboard's **Model Performance** tab.

| Feature set | Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---:|---:|---:|---:|---:|
| full | logistic_regression | 0.9979 | 0.9995 | 0.9970 | 0.9982 | 0.9973 |
| full | random_forest | 0.9997 | 1.0000 | 0.9994 | 0.9997 | 1.0000 |
| full | gradient_boosting | 0.9997 | 1.0000 | 0.9995 | 0.9997 | 1.0000 |
| **realistic** | logistic_regression | 0.8878 | 0.9314 | 0.8775 | 0.9037 | 0.9340 |
| **realistic** | **random_forest** ⭐ | **0.9199** | **1.0000** | **0.8665** | **0.9285** | **0.9430** |
| realistic | gradient_boosting | 0.9199 | 1.0000 | 0.8665 | 0.9285 | 0.9445 |
| minimal | logistic_regression | 0.6015 | 0.7130 | 0.5621 | 0.6286 | 0.6582 |
| minimal | random_forest | 0.6017 | 0.7099 | 0.5684 | 0.6313 | 0.6547 |
| minimal | gradient_boosting | 0.6294 | 0.6496 | 0.8301 | 0.7289 | 0.6571 |

⭐ = model loaded by the dashboard's prediction tab.

Note that `minimal` barely beats the ~60% majority-class baseline (60% of patients in
this dataset are diagnosed) — demographics and lifestyle alone carry little signal;
almost all of the real predictive power in `realistic` comes from `hba1c` and glucose
readings, confirmed by `random_forest`'s feature importances (`hba1c` at 46%,
`glucose_postprandial` at 17%, `glucose_fasting` at 9% — see the dashboard's
**Feature Importance** tab).

## Project structure

```
├── src/diabetes_prediction/   # the package: data loading, preprocessing, models, training, prediction
├── dashboard/app.py           # Streamlit dashboard
├── tests/                     # pytest suite
├── data/                      # dataset + data dictionary
├── models/, reports/          # generated by train.py (gitignored)
├── notebooks/                 # exploratory only, no pipeline logic
├── Dockerfile, Dockerfile.train, docker-compose.yml
└── .github/workflows/ci.yml
```

## Running locally

```bash
pip install -e ".[dev]"
python -m diabetes_prediction.train   # writes models/ and reports/
pytest
streamlit run dashboard/app.py
```

## Running with Docker

```bash
docker compose up train       # writes models/ + reports/ to the host
docker compose up dashboard   # serves at http://localhost:8501
```

`train` is excluded from a plain `docker compose up` (via compose profiles) since
it's a one-off batch job, not a long-running service — run it explicitly first.
